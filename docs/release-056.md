# SerbisyoGo 0.5.6 release decision

The [staging and release-blocker report](release-056-staging.md) records the subsequent recovery inventory, isolated rehearsal, map repair, remote workflow checks and pending approvals. Use its recovery and staging procedures for the current release hold.

**Hold the public release.** On November 19, 2026 the linked project's four public professionals all carried the development fixture marker. Migration 024 would expose zero professionals there. The backup inventory listed no backup and reported PITR disabled. Release requires a confirmed recovery point, a successful isolated restore, and a decision about the intended public catalog. Genuine approved providers with active services can populate discovery. An empty-directory launch needs an explicit product decision.

## Approved rollout and recovery

Record the reviewed Git SHA, staging evidence, backup reference and current Cloudflare deployment/version ID. Resolve the catalog decision before the migration because the existing live website reads the same public directory. Confirm the intended Cloudflare account/Worker and hosted Auth redirect, SMTP, Edge and storage configuration. Local packaging does not test CI secrets or deploy rights.

* **Database** — after explicit production approval, recheck the linked target and the two-file dry run, then run `npx.cmd --no-install supabase db push --linked`. Verify history, private record counts, public catalog, permissions and participant bookings/messages before proceeding.
* **Website** — after the release gates close, use the protected Cloudflare workflow on the reviewed main commit with `publish=true`, its full `reviewed_sha` and approval for `cloudflare-production`. Confirm the deployed assets, HTTPS, role dashboards and APK download. Keep the remote workflow disabled during the hold.
* **Android** — dispatch the reviewed main commit with its full `reviewed_sha`, `publish_release=false` and an empty `artifact_run_id`, then approve `android-signing`. Record the successful run ID, APK digest and certificate and complete device acceptance. Future publication requires a separate dispatch on main with the full `reviewed_sha`, `artifact_run_id`, `publish_release=true` and approval for `android-production`. Verify the release download before promoting the web manifest. [Android release workflow](../.github/workflows/android-apk.yml)
* **Recovery** — if a client fails after deployment, stop promotion and restore the previous Worker version via Cloudflare's deployment history. This reverts web assets only. Stop offering a faulty APK and prepare a higher-version signed correction for installed devices. For database issues prefer a reviewed forward correction preserving new bookings and messages. If a migration fails, inspect recorded versions and actual objects before retrying. A database restore requires separate operator authorization, a write freeze, a recovery-point decision and reconciliation of writes since that point. Reverify Auth, booking totals, Storage access and message membership before reopening. Never reset the linked production database. [Cloudflare Worker rollbacks](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/rollbacks/)
